System design

Studio PM

A self-hosted job management system built for one kind of work: packaging prepress and artwork. It replaces a manual spreadsheet with a pipeline: jobs arrive by email, a local AI reads them, operators pick them up, QC checks them, and every step is recorded.

Design complete · core logic written Next.js · PostgreSQL · Prisma Local AI with Ollama n8n · Microsoft Teams

How a job moves

From email to archive

Every job follows the same path. The AI does the reading and sorting, people do the work and the checking, and the system keeps the record.

  1. Email arrives AI

    The inbox is read every 2 minutes. The classifier sorts each email: new job, change request, client reply, or spam. Auto-replies and duplicates are filtered out before any AI call.

  2. Job details are read AI

    The job name is parsed into brand, job number, client reference, description, pack type and cutter size. A regex handles the studio's naming rule; the AI is only the fallback. Thai notes get a one-line summary, and a time estimate is suggested.

  3. Job enters the pool Everyone

    The job goes straight to the shared pool, with no waiting for approval. Fields the AI was unsure of are marked for review. The job folder on the NAS is found and linked.

  4. Claimed or assigned Operator · Manager

    An operator can take the job, or a manager can assign it from the top 3 suggestions. Whichever happens first wins, and a database lock makes sure only one does. If nobody picks it up in time, managers get an alert.

  5. Artwork and signed checklist Operator

    The operator works the job, logs time, then downloads a checklist PDF already filled with the job number and type. They tick it and sign it in Acrobat. On upload the system checks the job number, the signature and every checkbox before the job moves on.

  6. QC review QC

    QC approves or rejects with notes. A rejection sends the job back to the operator as a correction. After three rounds, the job is escalated to a manager.

  7. Sent and archived Operator · Manager

    The delivery is recorded: who sent it, how many files and when. The job is archived but never deleted, and stays searchable by any of its reference numbers.

Audit trail
    AI layer

    Five small agents, one local model

    All AI runs on the studio's own machine with Ollama and a single Qwen3 8B model, so there are no API fees and no job data leaves the building. Each agent does one narrow, structured task, and a person can always correct it.

    Agent 1

    Email classifier

    Reads the subject and the first 300 characters only. About 0.3 s per email. Possible duplicates go to a person instead of creating a job.

    Agent 2

    Job name parser

    Regex first, AI as fallback. Low confidence (under 0.7) marks the field for review on the pool card.

    Agent 3

    Thai notes summary

    Runs only when notes contain Thai script. Writes a one-line English summary for search. The original notes are never changed.

    Agent 4

    Time estimator

    Uses job type, print method, pack type, size and similar past jobs. Gives a suggestion with a confidence level, and improves as real times are logged.

    Agent 5

    Assignment scorer

    No AI at all: a plain SQL score. It ranks the top 3 operators for each job. A person always makes the final pick.

    score = brand experience × 0.4
          + available today × 0.3
          + light workload × 0.2
          + recent work on the brand × 0.1

    Deadlines

    SLA by client, job type and urgency

    Each job gets its deadline when it is created. The system picks the most specific rule that matches:

    • Client + job type + urgency
    • Client + urgency
    • Any client + job type + urgency
    • Any client + urgency (fallback)

    Time spent in every stage is recorded, so reports show where jobs actually wait.

    Reports

    Sent to Teams automatically

    • Daily, 6 PM: jobs done, in QC and overdue
    • Weekly: on-time rate, average time per job type, QC rounds
    • Monthly: full performance summary, top clients
    • Yearly: volume, trends, top brands, SLA performance
    • Tracked: estimated vs actual time, so the AI estimate can be checked
    Built to be trusted

    Rules that protect the data

    Nothing is deleted

    Deleting only hides a record. Every job, comment and change stays in the database.

    No lost updates

    Each job has a version number. If two people change it at once, the second gets a clear "reload" message instead of overwriting.

    One path for status

    A job's status changes in exactly one place in the code, which checks the role, the current status and the required input.

    Files stay where they are

    The system finds each job's existing NAS folder and never invents its own layout. If the NAS is down, jobs are still created.

    Backups in layers

    Database streamed to the NAS, a daily snapshot offsite, RAID on the NAS, and a printed restore runbook. Target: at most 15 minutes of data lost.

    Open API

    A versioned REST API with hashed, scoped API keys, so other studio tools and scripts can create and move jobs.

    Stack

    Simple, self-hosted parts

    • App: Next.js, TypeScript (strict), Tailwind, Zod validation
    • Data: PostgreSQL 16 with Prisma, full-text search
    • AI: Ollama running Qwen3 8B, English and Thai
    • Automation: n8n for email polling, Teams alerts and scheduled reports
    • PDF: pdf-lib reads signed checklists; Puppeteer renders reports
    • Server: one Mac Mini M4 (24 GB) in Docker, files on a separate NAS
    How it gets built

    Hard parts first

    The parts that are easiest to get wrong were written and tested first. A coding model then builds the rest in 22 small tasks, each with a clear "done when" check.

    • Written first: database schema, status workflow rules, permissions, NAS path rule, SLA rules, assignment scoring
    • Tested: 14 tests on the core logic that must stay green
    • Guard rails: 15 rules for the coding agent, such as one way to change status, no hard deletes, and checks before every commit
